## タイトル: GA4イベントを行動ごとに増やさず、パラメータで区別する

* **ステータス: 承認済**
* 意思決定者: stotic-dev
* 日付: 2026-08-22
* 技術的背景: [#196](https://github.com/stotic-dev/homete_iOS/issues/196) のオンボーディング計測追加、PR #209

## 文脈、背景や問題点の説明

オンボーディング（特典説明 → Paywall → 通知権限）の計測を追加するにあたり、当初は行動ごとに
`onboarding_premium_introduction_shown` / `onboarding_paywall_shown` / `onboarding_paywall_closed` …
と6つのイベント名を定義した。

GA4はプロパティごとに定義できるイベント名の数に上限があり、この調子で画面と操作の組み合わせぶんだけ
イベント名を増やすと、機能追加のたびに枠を消費して将来の計測ができなくなる。
どの粒度でイベント名を分けるべきか、方針を決める必要があった。

## 決定事項

* **イベント名は「機能・文脈」の単位で定義する。** 個別のユーザー行動ごとには増やさない
* オンボーディングの計測は `onboarding` イベント1つに集約し、
  `step`（画面） / `action`（操作） / `result`（結果）のパラメータで区別する
* パラメータのキーは機能をまたいで使い回す（GA4のカスタムディメンションにも登録数の上限があるため、
  `isGranted` / `isPremium` のような行動固有のキーを増やさない）
* `result` は真偽値の文字列ではなく、GAのレポート上でそのまま意味が読める語（`granted` / `denied` / `purchased` など）にする
* パラメータの組み立ては `<機能名>AnalyticsAction` enumに閉じ込め、Viewは行動を表すcaseを渡すだけにする
* 送信タイミングとパラメータの定義は [doc/analytics_events.md](../analytics_events.md) に集約し、実装と同時に更新する

## 考慮した選択肢

* **選択肢1: 行動ごとにイベント名を定義する**（当初の実装）
* **選択肢2: 機能単位のイベント名 + パラメータで区別する**（採用）
* **選択肢3: `screen_view`などGA4の自動収集イベントに寄せ、カスタムイベントを作らない**

## 決定結果

### 決定にあたり考慮したメリット

* イベント名の枠を圧迫しないため、今後の機能追加でも計測を足し続けられる
* 同じ文脈の行動が1イベントにまとまるため、GA上でファネル（表示 → Paywall表示 → 購入）を組みやすい
* パラメータ生成がenumに集約され、送信内容の一覧性・テスト容易性が上がる

### 決定にあたり考慮したデメリット

* GAの探索レポートで特定の行動だけを見たい場合、イベント名で絞るのではなくパラメータ条件を指定する手間が増える
* パラメータをカスタムディメンションとして登録するまでレポートで使えないため、初期設定の一手間が必要
* `action` の値が文字列のため、実装とドキュメントの対応付けを人手で維持する必要がある
  （そのため「イベント追加時はドキュメントも更新する」を [doc/analytics_events.md](../analytics_events.md) に明記した）

### 選択肢3を採らなかった理由

自動収集イベントは画面表示までしか捉えられず、「Paywallを開かずにスキップした」「通知を拒否した」といった
意思決定の結果が取れない。オンボーディング改善の判断材料としては不足するため採用しなかった。
