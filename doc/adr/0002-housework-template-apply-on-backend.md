## タイトル: 家事テンプレートの手動適用ロジックをクライアントから Cloud Functions に移行する

* **却下済**
* stotic-dev
* 日付: 2026-05-14（却下: 2026-05-14）
* 関連 Issue: #67、#139

## 却下理由

本 ADR は「テンプレート適用時に対象期間の `incomplete` 家事を削除し、テンプレートから家事を再生成して `Houseworks` コレクションに書き込む」処理を、クライアントから Cloud Functions に移行することを決定したものである。

しかし方針検討を続ける中で、**そもそも「テンプレート適用時に Houseworks コレクションに大量のドキュメントを生成する」設計自体が高コストである**ことが明らかになった。テンプレートは編集頻度が高い性質を持つため、編集のたびに過去・未来の各日付のドキュメントを再生成・更新する必要があり、Firestore の書き込みコストが現実的でなくなる。

代替案として「テンプレートの家事は Houseworks コレクションに書き込まず、`HouseworkBoardView` 表示時にテンプレート定義と既存 Houseworks をマージして仮想的に表示する」方式を採用することを決定した（[ADR-0003](0003-housework-template-virtual-view.md) 参照）。この方式では「テンプレート適用」という操作自体が存在しなくなるため、本 ADR の論点（適用ロジックの実装場所）は無効となる。

## 文脈、背景や問題点の説明

家事週間テンプレート機能（#67）では「手動適用」と「自動適用」の2種類の適用フローが存在する。当初の方針（`doc/strategy/housework_template.md`）では手動適用をクライアント（iOS）に、自動適用をバックエンド（Cloud Functions Scheduled）に実装することにしていた。

しかし両者は本質的に同じ処理（対象期間の `incomplete` 家事を削除し、テンプレートから家事を再生成し、`Cohabitant.appliedTemplates` を更新する）を行う。このまま実装を分けると、クライアントとバックエンドで適用ロジックを二重に実装することになり、片方の修正がもう片方に反映されないリスクが高い。

**手動適用と自動適用で重複する適用ロジックを、どこに集約すべきか？**

## 決定事項

* 手動適用・自動適用の双方で使用する「テンプレート適用の共通ロジック」を Firebase Cloud Functions 側に実装する
* 手動適用は Cloud Functions の Callable Function（`applyHouseworkTemplate`）として公開し、iOS クライアントは Client 経由でこの API を呼び出す
* 自動適用は Cloud Functions の Scheduled Function（`applyWeeklyTemplate`）から同じ共通ロジックを呼び出す
* 既存の `HouseworkListStore.applyTemplate`（クライアント側の適用処理）は本対応で削除する
* 上書き確認ダイアログなど、UI に関わる責務はクライアント側に残す

## 考慮した選択肢

* **手動はクライアント / 自動はバックエンド（当初方針）**: 実装の独立性は高いが、共通ロジックを二重に持つことになり保守性が低い。仕様変更時に両方を同期して修正する必要がある
* **クライアント側に共通ロジックを実装し、自動適用も含めてクライアント主導で動かす**: iOS 端末がオフラインの間は自動適用が走らず、複数ユーザーから同時に適用が走るリスクもある。実装上も「定期実行」をクライアントで保証するのは困難
* **手動・自動とも Cloud Functions の共通ロジックに集約（採用）**: 適用ロジックは1箇所のみで管理でき、自動適用追加時にも追加の重複実装が発生しない。クライアントは UI と Callable 呼び出しに専念できる

## 決定結果

### 決定にあたり考慮したメリット

* 適用ロジックの実装が Cloud Functions に1箇所に集約され、手動・自動の整合性が保証される
* 自動適用機能を後から追加する際に、共通ロジックをそのまま再利用できる
* Firestore のバッチ書き込みや権限チェックなど、サーバー側で実行した方が安全・効率的な処理を一貫してバックエンドで扱える
* iOS クライアントから適用処理に関するドメインロジック（対象期間内の `incomplete` 抽出・再生成）が消え、クライアントの責務が「UI と API 呼び出し」に明確化される

### 決定にあたり考慮したデメリット

* Cloud Functions の Callable Function を新設する必要があり、初期実装コストが増える（認証・権限チェック、E2E テスト整備）
* 適用処理のレイテンシがネットワーク往復分増える（ローカル処理に比べてユーザー体感の応答が遅くなる可能性がある）
* Functions のコールドスタートにより、初回呼び出し時に応答が遅延する場合がある
* オフライン状態では適用が実行できなくなる（ただしテンプレート適用は性質上オンライン必須の処理であり実害は小さい）
