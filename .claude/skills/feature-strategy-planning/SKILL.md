# 機能実装の方針決定スキル

GitHub Issue や機能要望を受けて、実装着手前に「要件 → 不明点解消 → 設計方針 → タスク」を `doc/strategy/<kebab-case>.md` に整理するためのスキル。

## 使用タイミング

- ユーザーが「このIssueの対応を行います」「〇〇機能を実装してほしい」と依頼してきた時
- 要件は決まっているが、実装方針・設計が未整理な状態
- 着手前に開発者と方針合意を取りたい時

**使用しない場合:**
- バグ修正など、要件が自明で方針整理が不要な小さい変更
- ユーザーが「すぐ実装して」と明示的に方針ドキュメント不要を伝えた場合
- 純粋なリファクタリングで仕様変更を伴わないもの

## 全体フロー

```
1. Issue/要件の読み込み・把握
   ↓
2. 関連コードを調査して文脈を獲得
   ↓
3. 不明点を整理して AskUserQuestion で確認
   ↓
4. 確定内容を doc/strategy/<kebab-case>.md に整理
   ↓
5. ユーザーに完了報告 + 実装フェーズへの進行確認
```

実装そのもの（コード変更）は本スキルの対象外。実装フェーズに進む前のドキュメント整備までを担う。

---

## Phase 1: 要件の把握

### 1-1. Issue を読む

```bash
# Issue URL が提供されている場合
gh issue view <issue番号> --repo stotic-dev/homete_iOS
# あるいはコメントも含めて取得
gh issue view <issue番号> --repo stotic-dev/homete_iOS --comments
```

### 1-2. ブランチ名・関連リソースを記録

- 現在のブランチ名（`git branch --show-current`）
- 関連Issue URL
- 親Issue / Epic がある場合は併記

### 1-3. 関連コードを調査

Issue の対象範囲に応じて、最小限の文脈獲得を行う。具体的には:

- 影響しそうな View / Store / Client / Domain モデルの実在確認
- 既存の類似機能の実装パターン（参考にできる導線）
- 関連する `AppRoute` / `RouteResolver` の現状

調査が広範囲に渡る場合は `Agent(subagent_type: "Explore")` の利用を検討。

---

## Phase 2: 不明点の抽出と確認

要件が曖昧な点・実装判断が分かれる点を洗い出す。よくある観点:

### よくある不明点パターン

| 観点 | 確認すべき例 |
|---|---|
| **UI 文言・アイコン** | メニュー項目のタイトル / SF Symbol 名 |
| **表示制御** | 常に表示 / 条件付き表示（状態による出し分け） |
| **表示方式** | sheet / fullScreenCover / NavigationLink / インライン |
| **状態遷移** | 完了後の挙動（dismiss だけか、画面遷移するか） |
| **エラーケース** | 失敗時の表示 / リトライの有無 |
| **空状態** | 0件時の表示（空View / プレースホルダ / 導線提示） |
| **権限・認証** | グループ未参加時の挙動 / 認証切れ時の処理 |
| **デザイン** | カラー / レイアウト（既存と揃えるか） |
| **データ取得タイミング** | 起動時 / 表示時 / pull-to-refresh |

### AskUserQuestion で確認する

不明点が3〜5個程度に収まるよう抽象化し、`AskUserQuestion` で**選択式**にして提示する。
各質問の選択肢には「推奨案 (Recommended)」を先頭に置き、開発者の判断負荷を下げる。

```
質問例:
- header: "表示方式"
- question: "RegisterCohabitantView の表示方法は？"
- options:
  - "fullScreenCover (Recommended)" — HomeView と同じ方式で統一感
  - "sheet" — モーダル感を弱める
  - "NavigationLink" — 戻る導線を出す
```

**注意:**
- 一度の `AskUserQuestion` 呼び出しで複数質問を投げられる（最大4問）。バラバラに聞かない
- 既存実装に追従するのが妥当な点は「(Recommended)」明示で誘導する
- 開発者が回答済みの内容を再度聞かない

## Phase 3: 戦略ドキュメントの作成

### 3-1. ファイル配置とファイル名

- 保存先: `doc/strategy/`
- ファイル名: `<kebab-case-feature-name>.md`
- 例: `setting-create-group-and-add-member.md`, `group-member-list.md`, `housework-points.md`

ファイル名は Issue タイトルや機能の本質を要約したkebab-case。ブランチ名と一致させると追跡しやすい。

### 3-3. テンプレート使用時のポイント

- **要件**: 「何をするか」を具体的に。「タップ時に〇〇する」「〇〇な場合は表示しない」のレベルまで落とす
- **設計方針**: 既存ファイルパスを必ず明記。コード例も「変更後の差分が想像できる粒度」で書く
- **ファイル配置表**: 変更/新規/削除を明示。実装フェーズで参照しやすい
- **タスク**: チェックボックス形式で進捗追跡可能にする。Phase 1〜4 の構造は固定
- **ステータス**: 上部のステータスは Phase の完了に応じて更新する

### 3-4. ADR が必要なケース

`.claude/rules/adr.md` に従い、以下のような場合は本スキルとは別途 `doc/adr/NNNN-<title>.md` を作成する。

- 採用するライブラリ・フレームワークの選定
- アーキテクチャパターンの採用・変更
- 複数の実装方針を比較検討した上で選択した場合
- 既存の技術的負債の解消方針を決定した場合

戦略ドキュメントには ADR へのリンクを追記する形でクロスリファレンスを張る。

---

## Phase 4: 完了報告

ドキュメント作成後、ユーザーに以下を伝える:

1. **確定した不明点の要約**（質問と回答のペア）
2. **主な設計方針**（3〜5項目程度）
3. **ドキュメントパス**: `doc/strategy/<name>.md`
4. **実装フェーズへ進む確認**: 「Phase 2 実装に進めて良いか」を尋ねる

例:

```
要件とタスクを doc/strategy/<name>.md に整理しました。

確認した不明点と回答:
1. <質問1> → <回答1>
2. <質問2> → <回答2>

主な設計方針:
- <方針1>
- <方針2>

実装に進めて問題ないか、または事前に修正したい点があれば教えてください。
```

## 注意事項

1. **実装には踏み込まない**
   - 本スキルの責務はドキュメント作成まで
   - コード変更はユーザーから明示的に「実装を進めて」と指示があってから

2. **不明点ゼロを目指す**
   - ドキュメント作成前にすべての判断分岐をユーザーと合意済みにする
   - 実装中に「これどっち？」が出ないレベルまで詰める

3. **既存パターンに従う**
   - 過去の `doc/strategy/` ドキュメントと構造を揃える
   - 機能要望ごとに勝手な独自フォーマットを作らない

4. **Phase の進捗に応じてドキュメント更新**
   - 実装が進んだら該当チェックボックスを `[x]` に更新
   - 設計に変更があった場合は「設計方針」セクションも追従

5. **関連スキルとの連携**
   - 検証時: `swift-code-verification` スキルを使用
   - PR作成時: `pr-create` スキルを使用
   - Issue起票時: `issue-create` スキルを使用（本スキルとは別タイミング）
