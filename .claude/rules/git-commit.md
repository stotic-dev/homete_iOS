# Gitコミットのルール

## 対応ごとにコミットを分ける

**1コミット = 1つの対応**。1回のターンで複数の依頼・複数の指摘に対応した場合も、まとめて1コミットにせず対応単位で積むこと。

理由は、コミットが後から効いてくる場面がすべて「対応単位」で動くため。

- レビューはコミット単位で追える方が差分の意図を掴みやすい
- 片方の対応だけ問題が見つかったとき、`git revert` で個別に戻せる
- `git bisect` で原因コミットを特定したとき、対応が混ざっていると絞り込めない
- コミットメッセージが「AとBとCをやった」になる時点で、後から読む人はどの変更がどの目的だったか判別できない

### 分割の単位

| 状況 | コミット |
|---|---|
| レビュー指摘を3件修正した | 3コミット（関連する指摘同士なら1つにまとめてよい） |
| 機能追加＋そのユニットテスト | 1コミット（テストは実装の一部） |
| 機能追加＋既存コードのリファクタリング | 2コミット（リファクタを先に積む） |
| 機能追加＋ドキュメント/ADR更新 | 2コミット（`feat:` と `docs:`） |
| 実装＋設計ルール（`.claude/rules/`）の追加 | 2コミット |

**プレフィックスが1つに決まらないなら分割のサイン。** `feat:` と `docs:` と `refactor:` のどれを付けるか迷ったら、その時点で複数の対応が混ざっている。

### ステージング

`git add -A` / `git add .` で一括ステージしない。対応ごとに `git add <path>` でファイルを選んで積む。1ファイル内に複数の対応が混ざってしまった場合は、可能なら実装時点で順番に対応してコミットしていく（後から分割するのは困難なため）。

### 検証との関係

ビルド・SwiftLint・ユニットテスト（[swift-code-verification](swift-code-verification.md)）は変更が出揃ったタイミングで1回流せばよい。**検証の回数とコミットの粒度は別問題**で、検証コストを理由にコミットをまとめない。

## コミットメッセージ

`<prefix>: <日本語の要約>` の形式。

プレフィックスは Conventional Commits に準拠する。

| prefix | 用途 |
|---|---|
| `feat` | 機能追加 |
| `fix` | バグ修正・不具合対応 |
| `refactor` | 挙動を変えない内部改善 |
| `test` | テストの追加・修正 |
| `docs` | ドキュメント（`doc/`、`CLAUDE.md`、ADR） |
| `chore` | ビルド設定・ツール設定・依存更新・Claude Code設定 |
| `ci` | GitHub Actions / Xcode Cloud のワークフロー |

要約は「何をしたか」を体言止めまたは動詞で簡潔に。詳細な理由が必要な場合は本文に書く（PRの説明で補える内容は本文に書かなくてよい）。
